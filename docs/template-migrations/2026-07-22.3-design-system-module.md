# The template ships a design-system module

`:platform:client:ui` (package root `platform.ui`) is new: a token layer, one primitive, and a
`design-system/` docs folder whose every image is a committed Paparazzi golden. The architecture
rules already described `:platform:client` as the home for a design system; nothing scaffolded it
until now.

The app root installs it once — `App()` wraps navigation in `<Prefix>Theme` and
`Provide<Prefix>Viewport` instead of a bare `MaterialTheme` — and `:feature:core` consumes one
primitive so the module is exercised rather than dead.

The palette and typography that ship are **neutral placeholders**, not an identity: a greyscale with
a restrained accent, and system typefaces.

## Detection

A project is affected if it has no design-system module:

```bash
test -d platform/client/ui || echo "no design-system module"
```

**If the project already has its own design system, you almost certainly want to keep it.** This
migration is for projects that have none. Adopting the template's module over a real, authored
system would be a downgrade — the template's is a scaffold. In that case take only what is useful
(the doc-surface pattern, the doc-image test) and skip the rest.

## Migration

1. Copy `platform/client/ui/` from the template and add `include(":platform:client:ui")` to
   `settings.gradle.kts`.
2. **Rename the type prefix.** The module ships with the template's `Ukpt` prefix; your project uses
   its own. `Ukpt` is the project type prefix that `ProjectRenamePlanner` already rewrites, so the
   same rename that produced your project's other types applies here — `UkptTheme` →
   `<Prefix>Theme`, `UkptColors` → `<Prefix>Colors`, and so on, including in the
   `design-system/` pages.
3. Add `implementation(projects.platform.client.ui)` to the client modules that will use it, and to
   `:app:client:common`.
4. In `App()`, replace the `MaterialTheme` wrapper with `<Prefix>Theme { Provide<Prefix>Viewport { … } }`
   **above** the navigation container, so every destination renders inside it and no screen wraps a
   theme of its own. `<Prefix>Theme` wraps a `MaterialTheme` derived from the tokens, so existing
   material components keep working and inherit the palette.
5. Author the identity — palette, type scale, typefaces, the principles' wording and the prohibition
   list. This is a design task, not a migration step; the `ukpt-design-system` skill drives it.
6. Re-record snapshots. Screens now render on the design system's palette and type scale, so
   goldens change. Review the diffs visually rather than accepting them wholesale.

Decide early what primitives are built on — Material3, Compose Unstyled, or bare `foundation` as the
scaffold does. Converting later is a rewrite. See `design-system/README.md` →
"What to build primitives on"; the scaffold's from-scratch button is a worked example of the shape
of a primitive, not a finished component.

## Verification

```bash
./gradlew :platform:client:ui:verifyPaparazzi --no-configuration-cache --max-workers=2
./gradlew :platform:common:architecture:verifyArchitecture --max-workers=2
```

The module's own suite includes `DesignSystemDocImagesTest`, which fails if a `design-system/` page
links to an image that does not exist — so a renamed doc-surface test cannot silently leave a hole
in a page. Then run the app and confirm screens render on the new palette: the theme is only
actually installed if `App()` wraps navigation in it.
