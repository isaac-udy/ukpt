# Feature packages are side-first: `feature.<name>.<side>.<layer>`

The axis-first feature packages (`feature.x.domain`, `.ui`, `.data`, `.services`) are replaced by a
side-first taxonomy. The root `feature.<name>` holds the shared wire vocabulary — the models,
exceptions, and constants both sides speak, declared in `:api`. One level down is a side, `client`
or `server`; two levels down a layer: `client.ui` / `client.domain` / `client.data`, and
`server.services` / `server.domain` / `server.data`. Publication to `:api` is a module move that
never changes a package.

## Detection

The project is affected if any feature source declares an axis-first package: a `feature.<name>.*`
package whose first segment after the feature name is `domain`, `ui`, `data`, or `services` rather
than `client` or `server`. After the catalog sync (`2026-07-31`), `verifyArchitecture` reports every
such declaration under the membership and `ModuleRules.sidePackageMatchesModule` tests.

## Wire safety comes first

**Do not move any package until every polymorphically-serialized type pins its discriminator.** A
`@Serializable` type reachable from polymorphic dispatch — a sealed variant, an Enro
`NavigationKey` — that pins no `@SerialName` uses its fully-qualified name as the wire value, so a
package move silently breaks stored JSON, captured requests, and browser history.

1. Audit every mechanism that could encode an FQN: sealed hierarchies in `@Serializable` payloads,
   navigation keys (serialized into web history), anything persisted as JSON.
2. Pin `@SerialName` on every participant, using the type-nesting chain from the outermost
   declaring type, package-free (`"StoredSession.ProcessingStatus.Complete"`); a navigation
   destination pins exactly `"NavigationKey.<Name>"`. `ProjectRules.serialNamePinnedOnPolymorphicTypes`
   and `ProjectRules.serialNameEncodesEnclosingType` enforce both halves.
3. Only then move packages — they are free once this holds. **Type renames never are.**

## Migration

Migrate one feature at a time, most-depended-upon first, and take each feature all the way — a
feature arrives when its packages are side-first and the suite is green for it; a half-split
feature fails the membership tests in both shapes.

Per feature:

- **Root**: models/exceptions/constants that cross the wire (or that both sides name) move to
  `feature.<name>` in `:api` — the `FeatureRules.Shared*` constructs. Everything else in the old
  `domain` package is side-private and moves down a side.
- **Client**: close to a rename. `ui` → `client.ui`, `data` → `client.data`; client-private domain
  logic → `client.domain`. A domain interface consumed only inside `:client` belongs in `:client` —
  minimal visibility; publish to `:api` (a file move) when a second feature needs it.
- **Server**: design work, not a rename. `services` → `server.services` keeps only the contract and
  entry points (`ServiceImpl`s). Each public storage function reached from `services` is restated
  as a `server.domain` interface — or folded with its siblings into a UseCase when the logic spans
  several — and the old storage/internal code becomes `server.data` (Repositories and
  StorageClasses) behind those interfaces. `services.internal` no longer exists as a concept.
- **Goldens**: snapshot goldens are directory-grouped by the preview's package, so they move with
  it (`snapshots/images/feature/<name>/ui/…` → `…/feature/<name>/client/ui/…`); `verifyPaparazzi`
  confirms the images still match.

## Verification

Per feature: `verifyArchitecture` green for that feature's declarations (membership,
`ModuleRules.sidePackageMatchesModule`), the full compile sweep, and the feature's tests. At the
end: zero axis-first packages remain (`grep -r "package feature\." --include="*.kt" | grep -vE
"\.(client|server)\.|feature\.[a-z]+$"` finds nothing unexplained).
