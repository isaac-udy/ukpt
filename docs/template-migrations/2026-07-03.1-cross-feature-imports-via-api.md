# Cross-feature imports must resolve to `:api` code

`ModuleRules.crossFeatureCodeViaApi` is a **new** tested rule: code in one `feature.[name]`
namespace must only depend on another feature's code that is declared in an `:api` module. Between
modules this was already enforced by the module-graph rules; the new rule adds the same guarantee
*within* a module that hosts several feature namespaces (the `:feature:core` starting pattern), so
every feature stays liftable into its own module.

`DomainLayer.crossFeatureViaApi` and `ServicesLayer.crossFeatureViaApi` now list it as an
enforcing rule.

## Detection

The project is affected if a feature module (typically `:feature:core`) hosts more than one
`feature.[name]` package namespace and any of them import another namespace's non-`:api` code.
`verifyArchitecture` reports each violating import after the rule sync.

## Migration

For each violation, either:

1. Move the shared type to the owning feature's `:api` module (the usual fix: the type is a
   domain object or contract both features need), or
2. Refactor the dependency away (the importing feature defines its own type, or the coupling
   moves behind a domain interface), or
3. With explicit sign-off, add an `@ArchitectureException` citing
   `ModuleRules.crossFeatureCodeViaApi` — this defers the lift-blocker rather than removing it.

## Verification

`verifyArchitecture` passes with no new exceptions, or with exceptions the user has signed off.
