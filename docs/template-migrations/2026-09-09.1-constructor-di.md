# Explicit constructors for dependency injection

Two enforced rules, a construct, and a graph-resolution test. A class a Koin module registers
gives no constructor parameter a default value, every application class is bound by constructor
reference, and the `:app` shells keep their module lists where a test can verify them.

Origin: a server whose worker graph failed at the first request because a UseCase bound with
`singleOf` declared `cleanupTimeout: Duration = 15.seconds`. Koin resolves every parameter of a
constructor reference from the graph; the default never applied, and nothing bound `Duration`.
Architecture checks and a server start both passed.

## Rules

- **`ProjectRules.injectableConstructorsHaveNoDefaults`** (new, enforced): a class a Koin module
  registers, by constructor reference or by constructing it in a binding lambda, has no default
  value on any primary constructor parameter. A dependency is a required parameter, even one
  production always satisfies with a standard instance; a setting fixed for every deployment is a
  private property or constant; a setting that varies is a field of a typed configuration object
  the dependency module assembles. A data, value, enum, sealed, or abstract class constructed in a
  lambda is a value assembled by hand and keeps its defaults, as do wire models, UI state, and
  functions.
- **`ProjectRules.constructorReferenceBindings`** (moved from `FeatureRules`, widened): covers
  every Koin module in the project, platform and `:app` modules included, and reports any lambda
  that constructs an application class, not only the `X(get())` form. A lambda that constructs a
  data class, a third-party client, or binds a Repository property under its interface is not
  reported, and neither is a lambda declaring runtime parameters (`factory { params -> … }`).
  `FeatureRules.constructorReferenceBindings` remains as a restatement; an `@ArchitectureException`
  citing it must cite the `ProjectRules` id instead.
- **`ClientData.Configuration` / `ServerData.Configuration`** (new construct): a `data class`
  named `[Name]Config` or `[Name]Configuration` in a `data` layer, with `immutable` and
  `assembledAtTheCompositionBoundary` (constructed only in a Koin module file or an `:app`
  module). `ClientData.ClientDataImplementation` no longer classifies such a data class. A
  UseCase's configuration is a domain model of its side (`DomainModel.carriesConfiguration`
  guidance on both groups).

## Template files

- `app/server/src/main/kotlin/<namespace>/ServerDependencies.kt`: `serverDependencies(postgresConfig)`
  returns the module list `Server.kt` installs. `ServerDependenciesTest` verifies it with
  koin-test as one module: `module { includes(serverDependencies(config)) }.verify()`.
  `app/server/build.gradle.kts` adds `testImplementation(libs.koin.test)`.
- `app/client/common/src/commonMain/kotlin/<namespace>/ClientDependencies.kt`: `clientDependencies`
  is the list `App()` installs. `ClientDependenciesTest` in `jvmTest` verifies it the same way.
  `app/client/common/build.gradle.kts` adds `jvmTest.dependencies { implementation(libs.koin.test) }`.
  Koin's `verifyAll()` checks each module alone, so a dependency bound by another module reads
  as missing; the single including module is the form that checks the graph.
- `platform/server/postgres` binds `ExposedTransactionRunner` by constructor reference.
- Skills carried by the file sync: `ukpt-feature-slice` (dependency module template, wiring
  checklist), `ukpt-urpc-service` (host template), `ukpt-verify` (graph tests).

Koin's `verify()` checks that each registered constructor parameter type has a definition, without
instantiating anything. It treats a parameter with a default as optional and only warns; the
rule above closes that gap. It does not prove a lazily resolved entry point (a scheduled job, a
worker) resolves at runtime: add a test that resolves each such entry point from the real graph.

## Detection

```bash
./gradlew verifyArchitecture
```

Every failing `ProjectRules.injectableConstructorsHaveNoDefaults` names the class and parameter;
every failing `ProjectRules.constructorReferenceBindings` names the module file and the class it
constructs. Also:

```bash
# @ArchitectureException citations of the moved id
grep -rn "FeatureRules.constructorReferenceBindings" --include="*.kt" --include="*.md" .

# Koin module lists to verify
grep -rn "modules(" --include="*.kt" app
```

## Migration

1. For each reported parameter, decide what the default was standing in for:
   - a dependency (`clock: Clock = Clock.System`): drop the default and bind the type once, in the
     `:app` shell or a platform module (`single<Clock> { Clock.System }`);
   - a setting fixed for every deployment (`cleanupTimeout = 15.seconds`): move it to a private
     property or constant of the class;
   - a setting that varies between deployments or modes: move it into a `[Name]Config` data class
     beside the class (data layer) or a domain model (UseCase), bind it with
     `single { …Config(…) }` in the dependency module, and take it as a required parameter.
2. Replace each reported lambda binding with `singleOf`, `factoryOf`, `scopedOf`, or
   `viewModelOf`, keeping the lifetime it had. Values the lambda passed become configuration
   fields bound as above; environment reads move into the dependency module or the `:app` shell.
3. Tests construct the class with every dependency supplied. A fixed timeout is tested with
   virtual time, not by adding a constructor parameter to shorten it.
4. Create `ServerDependencies.kt` and `ClientDependencies.kt` as in the template, move the module
   lists into them, add the two tests and the `koin-test` dependencies. For each lazily resolved
   entry point, add a test that resolves it from the running graph.
5. Dependency-resolution failures fall inside the application's error and logging boundary:
   resolve a job's or worker's dependencies inside the request handler that reports errors, not
   before it.
