# Gradle configuration cache is now ON

`org.gradle.configuration-cache` flips from `false` to `true`. The full compile sweep (all six
targets, wasm included) and the architecture tasks are cache-clean; reusing the entry takes the sweep
from roughly 45s to 5s.

The old setting was accompanied by a comment blaming the Compose-MP / Kotlin-wasm web target —
`compileKotlinWasmJs` and the `compose.resources` tasks — for being config-cache-incompatible. **That
diagnosis was wrong.** Those tasks are fine. The actual offender was the template's own `.DS_Store`
purge in `app/client/web/build.gradle.kts`:

```kotlin
tasks.matching { it.name.contains("WasmJs", ignoreCase = true) }.configureEach {
    doFirst {
        val klib = layout.buildDirectory.get().asFile.resolve("klib")   // ← captures Project
        …
    }
}
```

A `doFirst` lambda declared in a build script that touches `layout` (i.e. `project.layout`) drags the
`Project` into the task's serialized state, which the configuration cache rejects. Because the filter
matched every task whose name contains `WasmJs`, it poisoned all seven of them — which is exactly the
set that appeared to "fail". The fix binds the directory to a local **inside** the configuration
action so the `doFirst` closes over only a `Provider`.

> A script-level `val` is **not** sufficient: it is a property of the script class, so the lambda
> still captures the script and the failure merely changes to `cannot serialize Gradle script object
> references`. The local must live inside the `configureEach` action.

## The two opt-outs

Two task families genuinely cannot use the cache and must be run with `--no-configuration-cache`:

- **`wasmJsBrowserDevelopment{Run,Webpack}`** — the Kotlin plugin's `KotlinWebpack` task holds a
  `Project` reference and an unserializable `SoftReference` (via `NodeJsRootPluginApplier`). Upstream;
  nothing to fix locally.
- **`recordPaparazzi` / `verifyPaparazzi`** — under the cache the R class is dropped from the test
  runtime classpath, so every snapshot test dies with `ClassNotFoundException: <module>.R`.

Both are documented in the `ukpt-verify` skill and the `ukpt-verify-web` /
`ukpt-feature-slice` skills.

## Detection

A project is affected if its `gradle.properties` still carries `org.gradle.configuration-cache=false`
(the template shipped it that way through `2026-07-13`).

If a project already flipped the flag itself and sees
`cannot serialize object of type 'DefaultProject'` or `cannot serialize Gradle script object
references` on `*WasmJs*` tasks, it has the same `.DS_Store` hack and needs the same fix.

## Migration

1. In `app/client/web/build.gradle.kts`, move the klib directory lookup inside the `configureEach`
   action so the `doFirst` captures only it:
   ```kotlin
   tasks.matching { it.name.contains("WasmJs", ignoreCase = true) }.configureEach {
       val klibDir = layout.buildDirectory.dir("klib")
       doFirst {
           val klib = klibDir.get().asFile
           if (klib.exists()) {
               klib.walkTopDown().filter { it.name == ".DS_Store" }.forEach { it.delete() }
           }
       }
   }
   ```
2. Set `org.gradle.configuration-cache=true` in `gradle.properties` and replace the stale comment.
3. Add `--no-configuration-cache` to every invocation of `wasmJsBrowserDevelopment{Run,Webpack}` and
   `record/verifyPaparazzi` in docs, scripts and CI.

More generally: when a task newly reports `cannot serialize DefaultProject` / `Gradle script object
references`, suspect a `doFirst`/`doLast` closure in a build script before blaming the plugin.
