# `validateTemplate` is scoped by repository kind

`validateTemplate` (the `TemplateRepositoryValidator`) now distinguishes the template repository
from a project generated from it, and scopes the template-repo-specific checks accordingly. A
downstream marker (`.ukpt/template.json`) carries a `project` rename map; the template's marker does
not — that is the signal.

In a downstream project the two **skill file-path** checks (`referenced path does not exist`,
`link target does not exist`) are skipped: a project legitimately omits surfaces the template ships
(no server, no web, a renamed package), so a skill citing `app/client/web/build.gradle.kts` should
not fail its build. Every other check still runs downstream, including the genuinely useful
migration-date check and the architecture **rule-id** check (which resolves against the project's own
generated rule index).

## Detection

The project is affected if `./gradlew validateTemplate` previously failed with
`referenced path does not exist: …` or `link target does not exist: …` for surfaces the project
deliberately lacks — and if `.ukpt/template.json` contains a `project` block (which it must, for the
update skill to run at all).

## Migration

No code change is required — the behaviour ships in `build-logic/` and arrives with the update. After
updating:

1. Re-run `./gradlew validateTemplate`; the skill file-path failures for absent surfaces are gone.
2. If the project documented those failures as an expected/known deviation (for example a note in
   `AGENTS.md`), retire that note — the task now passes.

## Verification

`./gradlew validateTemplate` passes. `./gradlew -p build-logic test` passes, including the new
downstream case in `TemplateRepositoryValidatorTest`.
